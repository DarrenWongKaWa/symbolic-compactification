## 一句话

项目分两层，状态不同：

- **单纯的符号推导**（不读论文，由人或 AI 直接写出表达式交给引擎判定）：这是项目最扎实的部分。所有基准里引擎从没判错过，强模型用它时大部分推导步骤都能拿到机器证据。
- **读论文审稿**（从论文 LaTeX 逐字读出公式再判定）：判定一直是对的，但覆盖率低，也没有让 AI 多查出错误。作为“自动审查整篇论文”的产品，不值得继续做。

开发已暂停。如果继续，建议以第一层为核心，把它定位成 AI 做推导时的验算器。

## 项目现在能做什么

- **Compactify：** 化简给定表达式。模型提出候选，程序检查残差。
- **论文审计：** 清点编号公式，重建推导关系，生成审稿用的 HTML 和 Markdown。
- **多体物理核对：** Matsubara 求和、渐近余项、Langreth 规则、算符恒等式、格林函数积分。
- **步骤卡和步骤账本**（本轮新增）：
  - 一步写成“式 X → 式 Y，用到关系 R”，所有公式必须从论文原文逐字引用。
  - 每条 LaTeX 引用由两个独立读取器各读一遍，结果一致才算读成：一个是工具自己的读取器，另一个是 SymPy 的 `parse_latex`。
  - VALID 必须附显式余因子证书。INVALID 必须附精确的有理数反例，而且反例要满足引用的关系和论文规定的取值范围。
  - 每一步分为六类：代数、求和逐项、积分、极限、近似、定义。只有前两类由工具判定，其余列在审稿页上交给人。

规模：约 2.6 万行 Python，1,370 个测试全部通过，对抗测试集 110/110 判定不变，CI 通过。自 2026-08-19 起共 542 次提交、25 个 PR。

## 单纯的符号推导（不读论文）：现状

这一层不涉及读取 LaTeX，表达式由人或 AI 按卡片语法直接写出。有三种用法：

- **化简（compactify）：**给定一个表达式，模型提出更短的等价形式，引擎检查两者之差。只有差为 `ZERO` 才写出结果，并出具收据（输入哈希、定义域、假设）。“是否等价”和“是否更短”分开判。
- **正向推导：**每一步只有引擎判 `ZERO` 才算推进，`NONZERO` 或 `UNKNOWN` 都不推进。
- **逐步核对（步骤卡）：**一步写成一张 YAML 卡，引擎给出 `ZERO`、`NONZERO`（附反例）、`CERTIFIED_BY_RULE` 或 `UNKNOWN`。

引擎目前能判：有理和代数恒等式、级数系数、O(xⁿ) 余项、Matsubara 求和（精确留数）、费米加权积分、定积分、Langreth 规则、算符恒等式、可约差商、digamma 反射公式、Γ 极限级数。

**可靠性：所有基准里引擎都没有判错过。**

- 多体等价基准 v0（29 条断言）：回答 27 条，全部正确，没有一次把错误的断言判为成立。
- Guo 等人的 PRL 整篇：189 个编号式全部清点，146 个有原文依据的关系里 32 个精确 `ZERO`、21 个代入后 `ZERO`、11 个 `CERTIFIED_BY_RULE`；在 155 个对照项上错误提升为 0。
- 推导单 v1（32 步，埋 6 个错），历次结果：

| 时间 | 组别 | 判对 | 抓到埋错 | 误报 | 工具判定的步数 |
|---|---|---:|---:|---:|---:|
| 2026-09 第 1 轮 | Opus + 工具 | 32/32 | 6/6 | 0 | 12 |
| | Sonnet + 工具 | 31/32 | 6/6 | 1 | 13 |
| | Haiku + 工具 | 19/32 | 3/6 | 10 | 0 |
| 2026-09 第 2 轮（步骤卡 + cookbook） | Sonnet | 31/32 | 6/6 | 1 | 13 |

**问题在哪里**

- **准确率没有提升。**强模型不用工具也能做对，工具增加的是机器证据：最新一轮 Sonnet 有 25/32 步由工具判定，6 个错误中 5 个附精确反例。
- **小模型的瓶颈是“写卡片”，不是引擎。**Haiku 的错误都出在转写和约定上：抄错式子、漏项、把约定写成恒等映射。严格的原文引用模式能保证写错的卡片不被判定，但没办法让小模型写对。
- **化简功能有收据机制，但没有做过系统评测。**它到底能把表达式化简多少、在哪类表达式上有用，目前没有数据。

**判断：**这一层可以保留。它适合给强模型做推导时当验算器，把“我觉得对”变成“有可复核的证据”。它不负责发现错误，发现错误靠的是模型自己。

## 评测：同一个 AI 用不用这个工具，有什么差别

每组只跑一次。所有埋入的错误都先用数值方法独立确认过。

| 任务 | 模型 | 不用工具 | 用工具 | 工具自己判定的 |
|---|---|---|---|---|
| 推导单（32 步，埋 6 个错） | Sonnet | 32/32，6/6 | 32/32，6/6 | 25 步，全部正确；6 个错中 5 个由工具给出反例 |
| | Haiku | 26/32，0/6 | 26/32，0/6 | 0 |
| 审稿：1002.4692（埋 4 个错 + 原有 3 个错） | Opus | 7/7 | 7/7 | 1 个 INVALID，8 个 VALID |
| | Sonnet | 6/7 | 7/7 | 1 个 VALID |
| | Haiku | 3/7 | 2/7，误报 1 | 0 |
| 审稿：1708.01124（埋 4 个错 + 原有 2 个错） | Opus | 6/6 | 6/6 | 6 个 VALID；有 2 个错被防护压下，没有判 INVALID |
| | Sonnet | 4/6 | 6/6 | 2 个埋入错误由工具判 INVALID |
| | Haiku | 0/6，误报 1 | 1/6 | 0 |

13 篇论文共 651 步的账本里：

- 代数步骤判定了 32/177（18%），求和逐项步骤判定了 4/47。INVALID 为 0。
- 427 步（66%）是积分、极限、近似或定义，按设计交给人。
- 能判的步骤中，卡住的有 188 步：
  - 75% 是 LaTeX 读不了（`\int`、`\partial`、`\langle`、宏等）；
  - 20% 是防护为避免误判而压下；
  - 5% 是引用的关系在数学上推不出结论。

这一周写账本的 agent 发现了 2 个会导致误判的缺陷，都已修复并加了测试：

- 宏里的下标改名没有生效，导致一个正确的步骤被判成 INVALID。
- `\Delta T` 被读成 Δ×T，导致 `ΔT/ΔV = T/V` 被判成 VALID。

## 去留评估

**外部现状**

- 需求是真的。用 GPT-5 检查 NeurIPS 和 ICLR 论文，平均每篇有 3.8 到 5.9 个客观错误，一半以上是公式和推导错误，人工复核准确率 83%（[arXiv:2512.05925](https://arxiv.org/abs/2512.05925)）。
- 纯 LLM 审稿工具已经很多：Refine.ink、Reviewer3、Black Spatula、YesNoError 等。最好的配置能抓到 71.6% 的埋入错误，用户抱怨最多的是误报（[arXiv:2606.19749](https://arxiv.org/abs/2606.19749)）。
- 在 FLAWS 基准上，最强模型在前 10 个候选里只找到 39% 的关键错误（[arXiv:2511.21843](https://arxiv.org/abs/2511.21843)）。
- 形式化路线（Lean / [PhysLean](https://github.com/HEPLean/PhysLean)）严格，但每篇论文成本很高。
- 目前还没有人提供“绑定原文、出具精确证书”的论文推导核对产品。

**核心矛盾**

1. 工具的价值来自可信的证据，而可信要求逐字读原文。
2. 逐字读真实论文的 LaTeX 正是瓶颈，误判缺陷也来自这里。
3. 改成让 AI 转写，覆盖率能从 18% 提到大约 60–80%。但这样证据就退化成“AI 转写的式子是恒等式”，强模型自己写 SymPy 就能免费得到同样的东西。
4. 强模型本来就会自己写 Python 核对。这个包额外提供的只有防护、证书和审稿包，对需要信任结论的第三方有用，但不帮助找出更多错误。

**结论**

- 目标是多查出错误、覆盖整篇论文、或让小模型变强：不值得。
- 需要可复核的证据，比如审稿人要求可重复的核对、作者发勘误前想先确认，或者给 LLM 审稿结论做确认：值得，但市场窄。

## 想请教的问题

1. 在你看来，“可复核的机器证据”在哪个场景下真的有人需要：审稿人、期刊、作者，还是 AI 审稿系统？
2. 有一个大约 1–2 天就能做完的决定性实验，值得做吗？做法是：用现成的 LLM 审稿工具审 20 篇物理论文，把它报出的数学错误逐条交给本工具确认，看真错误被确认的比例和误报被否决的比例。
3. 积分、极限、近似这类步骤占了三分之二。有没有可信又不太贵的机器核对办法？候选是数值双转写、计算机代数和 Lean。
4. 是否应该允许 AI 转写公式，并把这类证据单独标注？
5. 还是把现有评测写成一篇方法和负面结果笔记，然后结束这个项目？
6. 如果继续，是否应该放弃读论文那一层，只保留“符号推导验算器”（化简、正向推导、步骤卡），并补做化简功能的评测？

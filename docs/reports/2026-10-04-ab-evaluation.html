结论

这个工具目前是一个“判了就可靠、但能判的很少”的核对器。它没有让模型多查出错误：Opus 和 Sonnet 不用它也能查出几乎全部埋入的错误，Haiku 用了它也查不出来。它的增加值是给出可复核的机器证据：在推导评测里，Sonnet 带工具时 32 步中有 25 步由工具判定，6 个错误中 5 个由工具给出反例，而且没有一个判错。

  • 可靠：这次评测中工具给出的每一个 VALID / INVALID 都是对的（推导评测 25 个，审稿评测在原文上 32 个，13 篇账本 36 个）。账本运行过程中由 agent 发现了 2 个会导致误判的缺陷，都已修复并加了测试。
  • 覆盖窄：13 篇论文、651 个推导步骤里，工具只判定了 36 步（约 6%）；只看它负责的代数步骤，是 32 / 177（18%）。积分、极限、近似这类步骤（427 步）一律交给人。
  • 查错靠模型自己：Opus 和 Sonnet 带工具的 4 组共面对 16 个埋入错误，全部查出；其中工具从原文引用直接判出的只有 3 个（短论文 1 个，长论文 2 个），其余是模型自己用 Python 数值核对找到的。

代数步骤没判定的原因

  • SOURCE_CHARACTER_UNSUPPORTED 70：读不了的 LaTeX（\int、\partial、\langle、\braket、现在还有 \Delta T）
  • GIVEN_UNREADABLE 31：引用的关系本身读不了
  • NAMED_QUANTITY_UNDEFINED 25：名字的值在别处给出
  • PARSE_FAILED 14，FUNCTION_OR_PRODUCT 9

找到反例但没有判 INVALID：32 条

防护的作用是宁可不判也不误判，代价是会漏掉真错。比如 math-ph/0303052 的式 28：论文印 64，按推导应为 69，引擎给出了精确反例，但正文在别处规定了 ω = μ = 1，工具分不清作用范围，于是压下。长论文 (16b)、(B4) 的埋入错误在 Opus 组里也是这样被压下的。

积分、极限、近似步骤的数值双转写

非代数步骤不判 VALID / INVALID。两个独立 agent 各自把一步写成 mpmath 代码，在同一组随机点上比较；只有两份转写彼此一致，结果才算数。

这次修掉的两个误判

宏里的下标改名没生效

账本可以把引用关系里的下标改名（p→L、q→R）。宏 \rpq 展开是 r_{pq}，改名碰不到宏内部，报告说改了、实际没改。一个正确的步骤因此被判成 INVALID。现在先展开宏再改名；改名没有起作用就拒绝这一步。

\Delta T 被读成 Δ·T

两个读取器都把 ΔT 读成 Δ 乘以 T，于是 \frac{\Delta T}{\Delta V} = \frac{T}{V} 被判 VALID。现在 \Delta / \delta 后面直接跟名字就拒读。代价：1708.01124 从 19 个 VALID 降到 10 个。后续可以把 ΔT 当成一个独立符号来读，并对这类步骤只给 VALID、不给 INVALID。

这次评测说明不了什么

  • 每组只跑了一次，Opus / Sonnet 的差别在一两个错误以内，不能当成稳定的排名。
  • 埋入的错误都是单个符号或系数，用 mpmath 逐式代数值就能查出。这类题对 Opus / Sonnet 太容易，测不出工具的上限价值。
  • 出题、做题、判分用的是同一家族的模型。
  • 评测 agent 被要求不读评测目录以外的文件，但这一点没有技术手段强制。

下一步建议

  • 换更难的题：选人工逐式数值核对代价很高的长推导（几十步、带约定和下标），这样才能看出工具对强模型的价值。
  • 让小模型真正用上工具：Haiku 两次都没写出能跑的账本。可以从一条命令的草稿自动生成账本骨架，小模型只需要填“用到哪个关系”。
  • 防护的作用范围：“正文别处写了 p = 1”会压下所有涉及 p 的反例。可以只在那一节或那个条件下生效，用测试证明不会因此误判。
  • ΔT 当成一个符号读，找回 1708.01124 的 9 个 VALID。
  • 数值双转写先固定参数表，否则大部分步骤得不出结论。
